# 三、用客户端自己把消息发出去

> 这是整套方案里**最脆弱的一环**，也是最能体现"工程细节决定成败"的地方。

## 1. 为什么要用"另一个客户端"发送

如果读库在 Android 模拟器里，发送却想快，有两条路：

1. 继续用 Android 客户端，靠 ADB 点界面 —— 一次 20 秒起步，太慢；
2. 在同一个模拟器里跑一个 **Linux QQ**（Termux + proot/chroot + Xvfb），用 xdotool 驱动 —— 一次 3–8 秒。

本文讲第 2 条。它需要一个已登录的 Linux QQ 和一个虚拟显示。

## 2. 环境

```bash
# 虚拟显示（1400x1000 够用）
Xvfb :98 -screen 0 1400x1000x24 &

# 客户端（需要先登录一次，之后勾选"自动登录"）
DISPLAY=:98 /opt/QQ/qq --no-sandbox &
```

## 3. 中文必须走剪贴板

`xdotool type "你好"` 在 Qt/Electron 应用里会被吞成 `???` —— 它按 keysym 逐个模拟，非 ASCII 没有对应键位。

**正确做法**：把文本写进文件，用剪贴板 PRIMARY 选择 + 鼠标中键粘贴：

```bash
xclip -selection primary -loops 3 < /tmp/msg.txt >/dev/null 2>&1 &
sleep 0.4
xdotool mousemove 560 668 click 2      # 中键粘贴
```

几个坑：

- `xclip` 默认会一直持有选择直到被替换，**要放后台**（`&`），否则脚本会挂住；
- `-loops 3` 让粘贴在多次消费后仍然可用；
- 粘贴前最好先 `ctrl+a`、`BackSpace` 清空输入框，避免拼接残留。

## 4. 发送流程

```
1. 切到目标会话（搜索框输入名字 + 回车）
2. 清空输入框（ctrl+a / BackSpace）
3. 中键粘贴
4. 截图比对输入框区域：没变化 → 粘贴失败，重试或放弃
5. 回车发送
6. 再次比对输入框区域：变空 → 有回执
7. ★ 回读客户端数据库：真的出现这条出站消息才算成功
```

第 4 步和第 6 步的"截图比对"是最廉价的动作确认；但**它不够**，原因见下一节。

## 5. 血的教训：UI 回执会骗人

真实故障：容器刚重启，客户端停在"没有打开任何会话"的空面板。

- 脚本照样点输入框 → 点空了；
- 粘贴 → 没有输入框，什么都没发生；
- 回车 → 没有反应；
- 截图比对：**前后都是空白，"]输入框被清空" → 判定"发送成功"`。

结果：程序以为发出去了，用户什么都没收到，而且后续每条都被"成功"骗过去。

**修复**：发送后再读一次客户端自己的数据库，确认最后一条出站消息的文本等于刚发的内容（允许几秒延迟，实测 1–20 秒内写入）。

```python
def verify_sent(target, text, timeout=20):
    deadline = time.time() + timeout
    while time.time() < deadline:
        last = read_last_own_message(target)     # 走第一节的库读
        if last and last["text"].strip() == text.strip():
            return True
        time.sleep(1.2)
    return False
```

## 6. 事务状态机与自愈

发送不是"成功/失败"二元，中间有"结果未知"。推荐状态机：

```
PREPARED → INPUT_COMMITTED → HANDOFF_UNKNOWN → UI_VERIFIED
                                    │
                                    ├→ MANUAL_REVIEW（人工核对）
                                    └→ ABORTED（确定没发）
```

规则：

- 只要存在**未结算**事务（`PREPARED / INPUT_COMMITTED / HANDOFF_UNKNOWN / MANUAL_REVIEW`），**拒绝任何新发送**（防止"可能已发出"时叠加第二次点击）；
- 但**必须配自愈**：每轮发送前，拿数据库核对未结算事务——
  - 库里能找到对应文本 → 补记为已发送，解锁；
  - 超过 N 分钟仍找不到 → 判为未发送（`ABORTED`），解锁。

没有自愈的 fail-closed，一次误判就会让机器人永久哑掉（我们踩过）。

## 7. 出站敏感词与能力边界

发送前加两道闸，顺序很关键：

```
1) 能力闸：明显做不到的请求（"帮我画张图"）→ 直接丢弃，不进模型
2) 内容闸：敏感词表命中 → 拒发（或打码），并记录 ABORTED
```

- 能力闸放在**入站**，省一次模型调用；
- 内容闸放在**出站**，因为模型可能自己写出不该发的内容；
- 拒发不要记成"结果未知"，否则会进人工核对队列、甚至触发熔断把目标静音。

## 8. 什么时候会坏

| 变化 | 后果 |
|---|---|
| 客户端改版、输入框位置变 | 固定坐标点击失效（表现：粘贴成功但发错地方） |
| 客户端改成虚拟列表 | 截图比对区域不再是输入框 |
| 系统缩放/分辨率变化 | 坐标全部偏移 |
| 会话面板被打开 | 输入框左移，坐标要跟着变 |

**缓解**：坐标全部参数化（放配置文件），并在发送前后各做一次"输入框区域是否变化"的检查；最坏情况是发送失败并告警，而不是发到错误的人那里。
